KG × LLM：領域知識內化

以保險顧問為例 / KG × LLM 聯合訓練 / CLM → SFT → DPO → PPO

2026.05 — 進行中 實支實付醫療險為案例

這個專案在做什麼。 把整套保險領域知識直接寫進 LLM 的權重 —— 不靠 RAG、不靠外掛 pipeline，靠的是把知識圖譜（KG）跟 LLM 一起訓練。 以實支實付醫療險為案例， 驗證「領域結構知識 + 完整訓練流程」這條路徑是否走得通。

為什麼需要四個階段（CLM → SFT → DPO → PPO）。 每一階段解的不是同一個問題 —— CLM 把保險的詞彙跟句型壓進 token 分布、 SFT 用（問題 → 條款回答）pair 教模型該怎麼答、 DPO 用偏好 pair 推該用什麼語氣答、 PPO 用 segment-level reward 修每一段該長什麼樣。 跳階段不是省事 —— 直接做 RL 會 reward hack（一個還不會講保險的模型，會找捷徑騙高分）； 跳過 DPO 直接做 PPO 會在錯誤的整體策略下細修，越修越偏。 先粗後細、先教會再優化，是這條訓練線的設計重點。

訓練流程大綱：CLM → SFT → DPO → PPO

整個專案的訓練線是四階段串接， 每一階段都用該技術本身的特性去推一段「分布上的偏移」 —— CLM 把下一個字預測納入保險語料、 SFT 用（問題→條款回答）pair 做條款層級對齊、 DPO 用 (chosen / rejected) pair 推風格偏好、 PPO 用 segment-level reward 做分段對齊。 每一階段都只訓 LoRA，base model 全程凍結， 每一階段都不宣稱讓模型「真的會推理」—— 只談技術能搬動什麼。

  • ① CLM 在保險領域文本上繼續做 next-token prediction， 讓模型「預測下一個字」的能力把保險的詞彙與條款句型 納入 token 分布。不教「怎麼回答」、也不教「結構」—— 只是讓領域語料的 perplexity 下降到合理區間， 為 SFT 提供詞彙基底。
    KG 注入：整條訓練線都有 KG 注入作為條款結構訊號 —— CLM 階段先打好讓 KG 結構訊號能對接的領域詞彙底座。
  • ② SFT 用（問題 → 條款相關回答）的 pair 做監督微調， 透過 CE Loss 把輸出方向針對條款做對齊， 讓模型擬合到「依條款內容作答」的分布。 重點在於：這是擬合訓練分布， 不是讓模型「真的會推理保險」—— 這個邊界要說清楚，後面 DPO / PPO 才有要解的問題。
    KG 注入：整條訓練線都有 KG 注入作為條款結構訊號 —— SFT 把條款的拓撲結構訊號跟回答 pair 一起進權重。
  • ③ DPO 在 SFT 權重上做偏好優化 —— 用 LLM 依原內容快速重寫產 chosen、 SFT 自身輸出當 rejected， 透過 DPO/IPO loss 把輸出往 chosen 的風格 / 表達方向推。 SFT 沒辦法靠 CE loss 引導的「語氣 / 反問時機 / 教科書腔」， 這一層用偏好訊號補。訊號粒度是整段，不是逐段。
    KG 注入：整條訓練線都有 KG 注入作為條款結構訊號 —— DPO 在已注入 KG 的權重基礎上做風格 / 表達層的偏好優化。
  • ④ PPO 用 reward model 對輸出的不同 segment 給不同 reward —— 本專案 PPO 的關鍵特性是 segment-level，不是 sequence-level。 DPO 給的是「整段比較」，做不到「這段該嚴謹引條款、那段該白話」這種粒度； PPO 用分段 reward 把這個粒度補上， 讓不同段落各自收斂到對應的標準。收斂效果仰賴 reward model 的品質。
    KG 注入：整條訓練線都有 KG 注入作為條款結構訊號 —— PPO 在已注入 KG 的權重基礎上，靠 RM 對不同 segment 的 span 分數做更動態的學習。

這個順序背後的取捨在每一節後面會逐步展開 —— 為什麼不能跳過 CLM / SFT 直接做 RL、為什麼 DPO 要在 PPO 之前、 以及每一階段的訓練架構圖（SFT / DPO / PPO 三張）會分別在對應章節呈現。

問題：缺乏鎖定問題的能力

目前大部分企業的做法是讓通用 LLM 搭配 RAG 處理領域問題 —— 用戶提問時，retrieval 從文件庫撈出相關段落，再交給 LLM 整理成回答。 這在開放域知識上 work 得不錯，但放到保險這種強結構領域， 回答的內容會變得過度發散： AI 看似把問題答得很完整，條款、條件、限額一股腦全列上來， 但使用者讀完反而抓不到自己真正要的那個重點 —— 字太多、訊號被噪音稀釋，「看起來有答」不等於「鎖住了問題」。

根本原因是 retrieval 撈出來的資訊量過大、而且高度碎片化。 這個碎片化不是技術選型的失誤，而是工程現實 —— 企業為了回答品質會選用最強的 LLM（例如 Claude Opus）， 但這類模型 token 成本高，沒辦法把整份條款直接塞進 context； 於是中間必須堆疊一連串前處理：提升檢索精準度、加上 reranker、 人工調 TopK、為不同問題類型客製 chunking 規則。

這些過程除了"非常不AI"，也不可能每個case都用相同的參數，都需要客製化調整。

三條解法路徑

上面的限制可以分三個方向處理： 要嘛在外部包更多層工程（更精的 prompt、多步驟流程、更聰明的 retriever） 把 RAG 撐起來； 要嘛跳過 retrieval，把領域知識直接內化進模型權重； 要嘛走第三條混合路徑 —— 保留 LLM 原本的通用推理能力， 同時在特定領域裡疊加一層結構化的推理與回答能力。 三條路解決的是同一個問題，但對「問題的根因」採取的立場不同。 本專案走的是第三條。

路徑一：結構化 prompt + 多步驟 pipeline

這條路徑承認 LLM 沒內化保險知識，但選擇在外部用工程補強： 預先設計好的 prompt template、問題分類、多步驟 retrieval、 結果重排、條件過濾，再交給 LLM 整理。目標是讓最終回答收斂在正確的條款上。

但這條路有幾個結構性的問題：

  • 無法泛用 這種客製化的回答 pipeline 沒辦法用一套參數通用到所有場景 —— 每個商品、每種問句風格、每個業務情境， 都得針對性調過 prompt、retrieval 參數跟 flow。 靠工程把單一情境撐起來，但模型自己沒辦法外推到下一個場景。
  • 沒解根因 知識仍在外部，只是用更複雜的方式取得 —— 把「模型沒內化」這個事實用工程複雜度遮蔽掉， 問題沒消失，只是被攤平到 pipeline 裡。
  • 耗時顯著增加 多步驟 pipeline 的每一步都要 LLM 呼叫一次 —— 問題分類 → 檢索 → 改寫 → 重排 → 生成， 整條 chain 跑下來，使用者等待時間遠長於單次 forward pass。 推論成本（時間 + token）隨步驟數線性疊加， 對話的即時感整個被工程鏈拖垮。

這條路徑在業界的代表是 Manus —— 靠 agent 編排跟工具鏈把通用 LLM 撐成處理複雜任務的系統。 能力廣，但底層限制就是上面這幾點： 客製化沒辦法泛用、知識仍在外部、每多一步就多等一段時間。

路徑二：把領域知識內化進模型權重

與其在推論階段把知識「找回來」，不如在訓練階段把知識「灌進去」。 在現有研究脈絡裡，「內化」的具體意思是： 透過訓練調整模型內神經層的參數， 讓領域知識本身進到權重裡 —— 使模型在沒有外部 retrieval 的情況下， 也能直接從權重產出帶領域知識的回答。 講白一點，就是把模型權重從「通用知識」狀態， 挪到「這個領域的問題我已經有答案輪廓」的狀態。

實作上，現有研究大多不採 full fine-tuning（成本太高）， 而是用 LoRA 這類 parameter-efficient 方法 —— 只訓練約原模型 0.1%–1% 的額外參數量 （依 rank 跟覆蓋的層而定），就能在原模型上疊一層「領域知識補丁」。

這條路徑帳面上的優勢：

  • 推論單純 沒有 retriever / reranker / 多步驟 pipeline，一次 forward pass 出答案。
  • 無 retrieval miss 回答從參數中回憶，不存在「沒撈到關鍵段落」的失誤。
  • 可端到端對齊 模型完全在訓練控制下，可以再接 RLHF / DPO / PPO 把「該嚴謹引條款」「該白話解釋」這類細粒度行為一起收進權重 —— RAG 系統難做到，因為 retrieval 是非可微環節，沒辦法跟 LLM 一起 reward 優化。

但這條路徑要誠實面對的風險，比帳面上看到的多得多：

  • 能力退化 Fine-tuning 過程可能讓模型在學新東西的同時， 丟掉原本的通用能力（catastrophic forgetting）—— 模型「會講保險」但「不會推理一般問題」的情況時有所聞。 對一個本來就是靠通用推理能力撐起回答品質的 LLM 來說，這是真實的成本。
  • 訓練不穩定 參數調整本身就有風險：可能 over-fit、 可能在某些任務上反而變差、可能 loss 收斂但實際輸出退步。 整個訓練過程要靠評估指標反覆驗證才能確定沒有退化， 「跑完一輪」不等於「訓練成功」。
  • 資料品質成本 壞資料會被直接寫進權重，後果比 RAG 撈到壞文件嚴重得多 —— RAG 改文件就能改，內化進權重的錯誤要再做訓練才修得掉。 data cleaning 的標準必須拉到很高， 高品質 SFT / preference 資料的整理成本，往往比訓練本身還高。
  • 更新需再訓練 條款一變要再做訓練，不像 RAG 改文件就好。

路徑三：混合架構（本專案路徑）

路徑一靠工程外掛遮蔽「沒內化」的事實，但答案發散、回應慢； 路徑二把知識內化進權重，但要承擔能力退化、訓練不穩定、資料品質這幾個真實的代價。 這兩條都不夠 —— 本專案探索第三條路：不是純微調，也不是純 RAG， 而是一種混合架構，目標是在不破壞 LLM 原本通用推理能力的前提下， 讓它在特定領域裡同時擁有結構化的推理路徑跟鎖得住問題的回答能力。

背後的取捨是： 純微調容易讓模型「會講保險，但忘了怎麼推理」； 純 RAG 又讓模型「會推理，但永遠抓不準條款結構」。 混合架構的設計目的是兩邊都保留 —— 通用推理留在原模型權重的軌道上， 領域結構知識則透過額外的訓練訊號（後面會講到的 KG 是其中一個關鍵部分） 以可控的方式進入模型，不蓋過原本能力， 又能在領域問題上產生收斂的回答。

這條路徑在方法上有幾個關鍵設計：

  • 凍結 LLM、只訓 LoRA LLM 內部的參數是高度耦合的（capability entanglement）—— 擅自調整原權重，容易在你沒看到的地方造成通用能力退化。 所以本方案先凍結原模型權重，只訓練 LoRA 的低秩更新， 把「動原參數」的風險先擋在門外。 未來如果訊號設計跟訓練流程被驗證夠穩定， 不排除逐步解凍部分權重做更大幅度的更新 —— 但那是後面才該問的問題。
  • LoRA 當低風險試金石 先做個技術澄清：LoRA 不是原模型的「微縮版」—— 它的低秩特性指的是更新矩陣是低秩的（ΔW = BA）， 原模型權重不變、被凍結。 它在這條路徑的真正角色是低成本、低風險的試金石： 用相對少的資料量先驗證「KG 注入方法 + 訓練流程」 能不能讓模型在領域問題上進步、又不傷到通用能力。 LoRA 跑得通，「要不要進一步解凍 LLM」這個問題才值得問； 連 LoRA 都跑不通的話，直接解凍只會把問題放大。
  • 用 KG 注入取代長 context 本方案採用知識圖譜注入跟 LLM 做聯合訓練， 取代「把整段條款／教材直接丟進 context」這種傳統長文本做法。 背後的思路借鑒 RAG 在 retrieval 上的核心優勢 —— 當訓練時餵給模型的訊號是已經結構化、定錨在正確條款上， 對 generation 的影響比餵一段平鋪文本直接得多。 KG 在表達「條款—條件—限額」這種拓撲關係上又比平面文本精確。 前提是兩件事得做對： （a）圖結構建得正確、 （b）模型能讀懂並利用這個圖結構 —— 這兩件事是這條路徑要驗證的核心命題。

具體的訓練流程跟結構訊號設計是後面幾節的主題： KG 怎麼跟 LLM 聯合訓練、為什麼要 CLM → SFT → DPO → PPO 這個順序、 每一階段在解什麼具體的子問題、 以及如何在訓練過程中監控通用能力沒被吃掉。

訓練流程：為什麼從 CLM / SFT 開始

要讓 base model 變成一個能用的保險顧問， 中間的訓練流程不能跳階段。每一階段做的事情不同， 少了任何一步，後面的階段都會出問題。

以下三節（SFT / DPO / PPO）各自附上一張訓練架構圖 —— 這三張圖都是本人針對保險顧問場景原創設計的訓練架構， 也是這個專案的核心研究產出之一。 建議搭配每節的文字一起讀， 圖能更快地說清楚資料流、loss 計算位置、跟 LoRA 更新的範圍。 每張圖點一下可以放大，方便看清細節。

CLM · 目標

用領域文本（條款原文、保險產業常見表述）做 next-token prediction， 讓 base model 熟悉保險領域的詞彙、句法與條款結構。 這個階段不教「該怎麼回答」，只教「保險的語言長什麼樣」 —— 暖身用，把通用 base model 對「給付上限」「等待期」這類術語 脆弱的內部表徵先補起來，後面階段才有穩的地基可以站。

CLM · 架構

整理中

CLM 階段不涉及 KG 注入，使用 base LLM + LoRA 在條款語料上做 standard next-token prediction。 架構與 SFT 共用 LoRA 主幹，差別只在沒有 graph encoder / adapter 路徑 —— 純語料、純 token loss。完整訓練架構圖整理中。

CLM · 輸出範例

整理中

CLM 的「輸出」不是回答 —— 在 token 分布層面動。 預計呈現的 diff：保險語料 perplexity 對比 (CLM 前 vs CLM 後)、 術語 next-token 預測準確度對比、條款典型句型的生成穩定度。 整理中。

SFT · 目標

SFT 是新知識真正內化進權重的核心階段 —— 這層做不好，後面再多 RL 對齊都救不回來。

有幾件事在這個階段必須做對：

  • 指令 SFT 是必做動作 把資料整理成（指令 / 使用者問題 → 回答）的 pair， 用cross-entropy loss (CE Loss) 訓練模型擬合到目標回答。 模型在每個 token 位置上學到「給定前面的 context，下一個 token 該是什麼」， 累積起來就把領域知識壓進了權重 —— 學習新知識的工作主要就在這個階段發生。
  • 資料品質直接寫進權重 CE loss 沒有判斷力，你餵什麼它擬合什麼。 壞資料、結構錯位的回答、含糊的條款引用，都會被原封不動學進權重。 這也是本專案用 KG 注入而不是直接堆原始長文本的原因 —— 訓練訊號本身就要在結構上是正確的， 不能指望模型自己從一堆平面文本裡推斷出條款的拓撲關係。
  • SFT 是「教會」、不是「修正」 SFT 只能模仿訓練資料：資料裡好的它學， 資料裡的偏誤（過度保證、該反問卻直接給答案、條款引述粒度錯誤） 它也照單全收。 這個層級的偏好問題交給後面的 DPO 跟 PPO 處理， 不是 SFT 該扛的責任。

SFT · 架構

LoRA + KG 注入：GAT 編碼器把保險條款的圖結構轉成 embedding， 透過 adapter 接到 LLM 的輸入序列上，跟條款文字一起進訓練。 CE Loss 在 answer tokens 上計算，base LLM 凍結、只訓 LoRA + Graph Encoder + Adapter。

Tips

為什麼不能跳過 CLM / SFT 直接做 RL

RL（DPO / PPO）做的是「優化」，不是「教會」。 一個還不知道保險語言長什麼樣的模型， 直接做 RL 會 reward hack： 找到一個能拿高 reward 但實質胡言亂語的策略。

順序是這樣的：CLM 給「能講」，SFT 給「會講」，RL 才有東西可以「優化」。 這個順序在小模型上特別重要 —— 容量小、容錯空間小，跳階段的後果會放大。

SFT · 輸出範例（KG 注入的初步效果）

對齊階段：DPO 跟 PPO 各自解什麼

SFT 後的模型雖然能講話，但有兩類問題沒解掉： 偏好不對齊（顧問該主動反問需求，模型常常直接給答案） 跟細粒度錯誤（該嚴謹引條款的地方變白話、該白話的地方變條文）。 DPO 跟 PPO 分別處理這兩件事。

DPO · 目標

DPO 在概念上很單純：準備（chosen / rejected）的成對資料， 用 loss function 讓模型直接往 chosen 那邊靠 —— 不需要訓練 reward model，訓練穩定、成本低， 帳面上看起來是 offline RL 裡最好上手的方法。

但實際在這個專案跑過之後，最反直覺學到的一件事是： 有 chosen 跟 rejected 不代表 DPO 能訓得好。 兩者的差距不能太大， 資料分布本身比成對的存在更關鍵 —— 如果只盯著訓練曲線上的 margin 看，幾乎一定會被誤導。

本專案最後的結論是：DPO 的訓練狀況必須三層並看，缺一不可。

  • 資料層 看 chosen / rejected 的 |Δlen|（長度差）跟 quality gap（品質差）。 長度差過大 → DPO 學到的是「長 = 好」的捷徑訊號； 品質差過大 → rejected 太容易被區分，模型壓根學不到細部偏好。 這兩個都要控制在合理區間，pair 才是真正在「教模型分辨偏好」。
  • 訓練層 看 margin（chosen vs rejected 的 log-prob 差）， 但只能當參考訊號，不是 ground truth。 margin 平穩上升只代表優化在動，不代表方向是對的 —— 模型可能只是把 rejected 樣態的 token 機率壓低， 對 chosen 的生成能力沒有實質提升。 單一 margin 數字會誤導，這是 DPO 最容易踩的坑。
  • 生成層 最後一定要落到生成階段的自訂指標來驗證 —— 像 sem_full（語意完整度）、has_surf（條款表層引用率）這類 跟領域目標直接對齊的訊號。 這層過了，前兩層的數字才有意義； 這層沒過，前兩層全是自我安慰。

所以 DPO 雖然是 offline 階段、表面上「有資料就能跑」， 但準備好成對資料只是入場券，不是通行證。 長度分布、品質落差、訓練監控、生成驗證 —— 每一層都要獨立把關，任何一層只看單一指標都會被誤導。

Tips · IPO（Identity Preference Optimization）為什麼存在： 上面說的「margin 一路上升、生成卻沒實質進步」， 根因是 DPO 的 log-sigmoid loss 沒有上界 —— preference 越乾淨、chosen 越明顯比 rejected 好的情境下， 模型會無止盡地把 chosen 的 logit 推高，policy 越走越遠離 reference model， margin 數字漂亮但生成已經偏掉。 IPO 把 log-sigmoid 換成 squared loss，loss 本身有界 —— 從損失函數設計上就把這條失敗路徑擋掉， 在 chosen / rejected 區分度高的場景下，IPO 比 DPO 穩定很多。 代價是學習訊號相對弱化，需要更多訓練步數才能收斂； 本專案在資料層品質落差難壓低的子集上採用 IPO 做替代驗證。

DPO 本身還有一個更根本的限制：訊號粒度是「整段比較」 —— 它知道 A 比 B 好，但不知道好在 A 的哪一段。 對某些細粒度的偏好問題不夠，這層交給後面的 PPO 處理。

DPO · 架構

續訓自 SFT 權重，把 (chosen / rejected) 成對資料送進 policy 跟 reference model 各算 log-prob， 再用 log-sigmoid（DPO）或 squared loss（IPO）算偏好損失 —— 沒有 reward model。 KG 不直接介入這一層；偏好優化建立在 SFT 已內化的條款結構上，DPO 只動風格分布。

PPO · 目標

用 reward model 評分模型輸出。 關鍵差別是這裡的 reward 不是給整段一個分數，而是對輸出的不同 segment 給不同的 reward， 讓模型在不同段落學到不同的標準 —— 需要嚴謹的地方有嚴謹的 reward， 需要白話的地方有白話的 reward。

這是 DPO 不容易做到的細粒度。代價是訓練成本比 DPO 高， 也需要 SFT 跟 DPO 已經把粗粒度問題壓下來， PPO 才能穩定收斂到細部優化。

PPO · 架構

policy / value / reference / RM 四個 model 同時參與，PPO clip + KL penalty 控制策略偏移。 本專案的關鍵特性：RM 對輸出的不同 segment 給不同 reward （而非整段一個分數），讓模型分段收斂到對應標準。

為什麼是 DPO 之後再 PPO

順序很重要。DPO 先把整體偏好對齊（顧問的角色定位、回答流程）， PPO 再做分段細修（每一段該長什麼樣）。 如果整體偏好還沒對齊就上 PPO， 模型會在錯誤的整體策略下做細修 —— 細修得越多離理想越遠。 先粗後細，是這條訓練線的設計重點。

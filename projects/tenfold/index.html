法律領域 RAG / Multi-Step Architecture / 驗證後的信心程度

2024.09 — 2025.06 Tenfold AI · Taipei

這是我加入新創公司 Tenfold AI 後打造的最一開始的產品 —— 一款法律顧問 AI Chatbot。法律是一個對「回答品質」要求極高的領域： 答案要引用正確的法條、要精確對應使用者實際的問題， 中間任何一步走偏，輸出的內容看起來像法律意見，但實際上沒辦法被信任。

一般 RAG 的做法在這個場景不夠用，因此我在 context 層設計了一套 法律領域特化的 Retrieval 機制， 並在整個回答流程上疊出一條多步驟架構 —— 搭配 Rerank、法規檢查等工具，最後把每個回答都附上驗證後的信心程度， 讓使用者不只看到答案，還能看到這個答案背後的依據強不強。

背景：法律領域的回答要求

法律問題跟一般客服問題的差別，不只是「需要更專業的詞彙」—— 而是對錯的標準不一樣。 一句「大致上正確」的回答在客服可以接受， 在法律場景就是錯的 —— 條號錯一個字、適用情境少一個前提， 整個結論就會跟著歪掉。

這對 RAG 系統提出兩個具體要求：

  • 引用要正確 撈回來的法條必須是真的存在、條號正確、版本對得上的條文 —— 不是「語意上接近」就好。 一般通用的向量檢索很容易撈到「字面相關但實際不適用」的條文， 這在法律情境是直接的事實錯誤。
  • 回答要精確 就算撈到對的條文，回答也要對齊使用者問題的具體情境 —— 同一條法律在不同情境下適用方式不同， 模型不能把條文照本宣科貼上來就交差。 必須能根據問題的具體條件，挑出條文中真正適用的部分。

這兩件事都不是把通用 LLM 接上一個普通 retriever 就能解決的。 整條 context pipeline 必須針對法律領域重新設計。

多步驟架構

為了把上面兩件事同時做對，我設計了一條多步驟（Multi-Step）的回答流程， 每一步只解決一個明確的子問題，再把結果交給下一步繼續處理。 這個架構不是把所有事情塞給單次 LLM 呼叫， 而是讓每一步都能用最適合的工具去做最對的事。

  • Retrieval 針對法律語料做特化的檢索 —— 從一般通用向量檢索擴展到能正確處理條號、法規版本、適用範圍的檢索層， 為後面的步驟提供乾淨、可信的素材。
  • Rerank 檢索回來的候選不是直接交給 LLM，而是經過 rerank 重新排序 —— 把「真正適用使用者問題」的條文推到前面， 讓 LLM 在生成時看到的是已經被篩選過的素材， 而不是一份排序粗糙的清單。
  • 法規檢查（Tool） 在生成階段加入法規檢查工具， 主動驗證模型引用的條文是否真的存在、是否被誤用、 是否跟問題的情境對得上。 這一步是法律 RAG 跟一般 RAG 最大的差別之一 —— 把「事實正確性」變成 pipeline 裡的可驗證環節， 而不是寄望 LLM 自己不要幻覺。
  • 回答整合 把通過檢查的條文跟使用者問題整合成最終回答 —— 保留法律引用的精確性，同時用使用者讀得懂的方式表達。

每一步都是獨立可驗證的環節，整條 pipeline 上任何一步出問題都能被定位 —— 這對一個面向法律專業的產品來說，比「黑盒模型給一個漂亮答案」重要得多。

迭代過程：準確率、效能與成本

這條 pipeline 不是一次到位 —— 整個 Tenfold 期間經歷多次改版， 從一個能跑但答得不夠準的雛形， 一路迭代到能交付給法律專業使用者使用的產品。 三個關鍵指標的具體進展：

  • 準確率 回答客戶問題的正確率從約 50% 提升到 95% —— 這個提升主要來自把單一 LLM 呼叫拆成可驗證的多步驟、 以及法規檢查工具把「引用對不對」這件事從寄望 LLM 變成可驗證環節。
  • 回應延遲 改用 LangGraph 重新編排， 把彼此沒有依賴關係的節點（例如不同類型的檢索與檢查） 抽出來做平行化執行 —— 只讓真正需要前一步結果的節點留在序列上。 最終 LLM response latency 提升 35%， 回答品質沒有退步。
  • Token 成本 搭配 prompt 精簡與 retrieval 結果的更嚴格篩選， 整體 token 使用量減少約 60% —— 少餵冗餘文本給 LLM，等於同時改善了延遲、成本、跟回答的訊噪比。

同時，pipeline 也根據使用者需求支援兩種輸出模式 —— 簡答給只想快速確認的情境， 詳答給需要看完整條文引用跟推論過程的情境。 同一條 multi-step pipeline 在不同模式下調整最後的整合步驟， 而不是切兩條完全獨立的流程， 確保兩種輸出的法律事實基底是一致的。

驗證後的信心程度

多步驟架構解決了「回答怎麼生出來」的問題， 但還有一個更根本的問題： 使用者怎麼知道這個回答可不可信？ 法律場景下，使用者面對 AI 的回答，要嘛全信、要嘛全不信 —— 中間缺少一個讓他「判斷依據強不強」的訊號。

因此每個回答都會附上一份驗證後的信心程度。 但這個分數的產生方式，才是這套系統真正不同的地方。

為什麼單純讓 LLM 打分數不夠

坊間多數工具的信心值都是直接讓 LLM 依規則自評 —— 給一段 prompt 描述評分標準，再讓 LLM 對自己的回答打 0–100。 這種做法看似合理，但在實際使用上會撞到一個結構性的問題： 分數鑑別度極低。

LLM 評分有強烈的整數偏好，輸出大量集中在 70、80、90 這幾個錨點上 —— 就算規則寫得再詳細，也很難讓模型穩定地分辨「81」跟「84」的差異。 結果是：一份「85 分」的答案跟一份「88 分」的答案， 在使用者眼中幾乎沒有差別， 分數本身退化成「過 / 沒過」的二元訊號， 失去了原本應該提供的細粒度可信度資訊。 這個問題不是規則沒寫好，而是把連續性的判斷 交給一個token-level 採樣模型本身就會發生的事。

本系統的做法：從反饋資料訓練專屬信心模型

我設計的做法是把信心評分這件事 從 prompt 規則改成可訓練的模型 —— 系統會持續收集客戶在使用時的反饋與修正 （哪些回答被採用、哪些被改寫、哪些被退回）， 把這些訊號當作標註資料，訓練一個專屬的信心模型。 這樣產生的分數來自實際使用情境的分布， 而不是 LLM 對自己作答的事後自評， 鑑別度自然遠超過 rule-based 的版本。

這個架構帶來兩個額外的延伸性：

  • 可遷移到不同領域 「什麼算有信心」在不同領域的標準不同 —— 法律可以接受的把握度，到了醫療場景就要再嚴格一階。 這套架構因為依賴該領域的標註資料而不是固定 prompt， 只要收集到對應領域的反饋， 就能訓練出符合該領域標準的信心模型， 而不是用同一套 LLM 規則硬套到所有產業上。
  • 可按公司客製化 同一個領域裡，不同公司對「好答案」的內部定義也不一樣 —— 公司 A 可能要求每個回答都引用條號， 公司 B 更看重語氣是否中立。 系統透過收集該公司內部的「好 / 不好」標註再訓練， 就能讓信心模型對齊該公司的評判標準， 而不是一份通用分數套到所有客戶。

關於揭露程度： 這套信心模型的訓練資料結構、特徵設計、與訓練流程的具體做法 受 Tenfold AI 保密協議限制，無法在此公開細節。 本節僅就設計動機與架構特性做說明。 整套信心模型由本人全權設計與開發。

整個信心分數的設計意義，比「多顯示一個數字」深得多 —— 它把 AI 從一個「給結論的黑盒」變成一個能被檢視、能跟著用法演進的助手。 使用者拿到的不只是答案，而是答案加上一份具鑑別度的依據強度， 能自己決定要不要進一步查證、或直接採信。 對需要為自己決策負責的法律場景，這層透明度是必要的，而不是加分項。
